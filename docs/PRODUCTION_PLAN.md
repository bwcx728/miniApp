# 上线改进计划

## 现状评估

当前项目是一个**单店美甲预约微信小程序的 V1 MVP**，已完成核心业务闭环（案例展示 → 预约申请 → 店员审核 → 状态回查），但仍处于**本地开发/UAT 阶段**，距离真正可上线的小程序还有明确的差距。

### 已完成的能力

- 顾客端：首页品牌展示、返图案例、预约申请、我的预约查询
- 店员端：预约规则配置、预约审核（通过/拒绝）
- 后端：Node.js HTTP API + SQLite 持久化，自测覆盖完整
- 身份：顾客 OpenID 主键、店员 OpenID 白名单

### 核心差距（阻塞上线）

| 维度 | 现状 | 上线要求 |
|------|------|----------|
| AppID | `touristappid`（游客模式） | 需注册正式 AppID |
| 微信登录 | Mock OpenID，前端手动输入 | 需接入 `wx.login` → 后端 `code2Session` 获取真实 OpenID |
| API 地址 | `http://127.0.0.1:3000` | 需部署到云服务器，配置 HTTPS + 备案域名 |
| 后端部署 | 本地运行 | 需 Docker 化部署或使用云托管/云函数 |
| 数据库 | SQLite 单文件 | 生产可保留 SQLite（单店足够），但需备份策略 |
| CORS | `Access-Control-Allow-Origin: *` | 小程序端无需 CORS（wx.request 不走浏览器），但需配置合法域名 |
| 图片资源 | `example.com` 占位图 | 需替换为真实图片，上传到 CDN 或微信云存储 |
| 错误处理 | 基础 toast 提示 | 需补充网络异常重试、超时处理、降级方案 |
| 安全 | 无请求签名、无防刷 | 需最基础的频率限制与输入校验加固 |

## 改进计划

### 阶段一：微信登录与真实身份接入（P0 - 上线必须）

**目标**：顾客不再手动输入 OpenID，使用微信授权自动获取。

#### 1.1 后端：接入微信登录

- 新增 `POST /api/v1/login` 接口
  - 接收前端 `wx.login()` 获取的 `code`
  - 调用微信 `https://api.weixin.qq.com/sns/jscode2session` 换取 `openid` + `session_key`
  - 生成自定义登录态 token（JWT 或简单加密 token）
  - 返回 token 给前端
- 新增环境变量：`WECHAT_APP_ID`、`WECHAT_APP_SECRET`
- 后续所有需鉴权接口从 token 中解出 openId，替代当前的 `X-Customer-OpenId` header

#### 1.2 前端：替换 Mock 身份

- `app.js` 的 `onLaunch` 中调用 `wx.login()` 获取 code
- 调用后端 `/api/v1/login` 换取 token
- 将 token 存储到本地（`wx.setStorageSync`）
- `utils/request.js` 统一在请求头注入 `Authorization: Bearer <token>`
- 移除开发环境的 mock OpenID 输入控件（或仅在开发环境保留）

#### 1.3 店员登录

- 店员同样走 `wx.login` 获取 openId
- 后端校验 openId 是否在白名单中
- 店员页面入口可通过首页的隐蔽入口进入（保持当前方案），但移除手动输入 OpenID

---

### 阶段二：服务端部署与域名配置（P0 - 上线必须）

**目标**：后端可通过 HTTPS 公网访问，小程序可在真机上正常联调。

#### 2.1 服务器部署

- **方案 A（推荐）：微信云托管**
  - 零运维，自动 HTTPS，免备案（使用微信提供的域名）
  - 支持 Docker 容器部署
  - 适合当前单店场景
- **方案 B：自有服务器**
  - 购买云服务器（阿里云/腾讯云轻量应用服务器）
  - 域名备案 + SSL 证书
  - Docker 部署 + Nginx 反向代理
  - 配置 PM2 或 systemd 管理进程

#### 2.2 Dockerfile 编写

```
FROM node:22-alpine
WORKDIR /app
COPY apps/server/ ./
RUN mkdir -p /app/data
EXPOSE 3000
CMD ["node", "src/server.mjs"]
```

#### 2.3 小程序域名配置

- 在微信公众平台后台配置 `request 合法域名`
- 前端 `app.js` 的 `apiBaseUrl` 改为环境变量控制（开发环境用本地、生产环境用线上地址）

#### 2.4 SQLite 数据持久化

- 挂载数据卷，确保容器重启不丢失数据
- 添加定时备份脚本（每天备份 SQLite 文件到对象存储）

### 阶段三：前端体验优化（P1 - 上线前建议完成）

**目标**：提升用户体验至可上线标准。

#### 3.1 真实图片与品牌内容

- 替换 `example.com` 占位图为真实美甲成品图
- 首页品牌区使用真实门店照片/logo
- Gallery 管理后期可通过后端接口动态维护

#### 3.2 加载与错误体验

- 页面加载时显示骨架屏（skeleton）而非空白
- 网络异常时提供"重试"按钮
- 预约提交成功后显示结果详情页（含预约时间、状态、门店地址）
- 登录失败时引导用户重新授权

#### 3.3 预约交互优化

- 日历选择组件优化：高亮可预约日期、置灰不可预约日期
- 时间段选择增加已约满标识
- 提交前增加确认弹窗（二次确认日期/时间段）
- 预约成功后跳转到"我的预约"并滚动到新建记录

#### 3.4 店员端体验

- 审核操作增加确认弹窗
- 预约列表支持按日期筛选
- 规则保存后显示"下次顾客看到的可预约范围"预览
- 新预约提醒（可先用轮询，后续升级为订阅消息）

#### 3.5 顾客到店提醒

- 审核通过后，在"我的预约"页显示到店提示（地址、注意事项）
- 后续可接入微信订阅消息，审核通过后主动推送通知

---

### 阶段四：安全与稳定性加固（P1 - 上线前建议完成）

#### 4.1 接口安全

- 添加请求频率限制（简单的 IP + OpenID 维度限流）
- 预约创建接口添加重复提交防护（幂等键或短时间内限制同一用户重复提交）
- 输入内容长度限制（姓名、手机号、备注等字段的最大长度校验）
- 手机号格式校验（后端也要校验，不能只依赖前端）

#### 4.2 数据安全

- 顾客手机号等敏感信息在日志中脱敏
- SQLite 数据库文件权限控制
- 定期数据备份

#### 4.3 监控与日志

- 添加结构化日志（请求路径、耗时、状态码）
- 接入简单的健康检查监控（可用 uptime 类工具定时检测 `/health`）
- 关键业务错误告警（如数据库连接失败、slot 冲突频繁）

---

### 阶段五：正式 AppID 与审核发布（P0 - 上线必须）

#### 5.1 注册与配置

- 注册微信小程序账号（个人主体或企业主体）
- 获取正式 AppID 和 AppSecret
- `project.config.json` 替换 `touristappid` 为正式 AppID
- 配置服务器域名白名单

#### 5.2 代码审核准备

- 确保小程序内容符合微信审核规范
- 补充用户隐私保护协议（如涉及手机号收集）
- 测试体验版本在多台真机上的表现
- 提交审核并处理审核反馈

#### 5.3 灰度发布

- 先发布体验版给门店员工和少量顾客测试
- 收集反馈并修复关键问题
- 正式发布

---

### 阶段六：后续增强（P2 - 上线后迭代）

以下功能不阻塞首次上线，但建议在运营初期逐步补充：

#### 6.1 订阅消息通知

- 顾客提交预约后 → 通知店员有新预约
- 店员审核后 → 通知顾客审核结果
- 预约当天 → 提醒顾客到店

#### 6.2 Gallery 内容管理

- 后端新增 Gallery CRUD 接口（店员可上传/编辑/排序返图案例）
- 图片上传到微信云存储或 OSS

#### 6.3 数据统计

- 店员端增加简单统计面板
  - 本月预约数、通过率
  - 热门时间段分布
  - 顾客回头率（基于 OpenID 统计重复预约）

#### 6.4 多时段支持

- 支持不同日期配置不同的时间段
- 支持特殊日期（节假日）单独配置

#### 6.5 技术架构演进

- 前端迁移到 Taro + React + TypeScript（提升开发效率和可维护性）
- 后端迁移到 NestJS + Prisma + MySQL（如果业务复杂度上升）
- 接入 CI/CD 流水线（GitHub Actions 或微信云托管的自动部署）

## 建议执行顺序

```
1. 注册正式 AppID + 域名备案（可并行启动，耗时最长）
2. 后端接入微信登录（POST /api/v1/login）
3. 前端改造登录流程（wx.login → 后端换 token）
4. Docker 化 + 部署到云托管
5. 配置服务器域名 + HTTPS
6. 替换真实图片资源
7. 前端体验优化
8. 安全加固
9. 体验版内测 → 收集反馈 → 修复
10. 提交微信审核 → 正式发布
```

## 结论

当前项目的业务逻辑和代码质量已经具备上线基础，**主要差距集中在基础设施层面**（微信登录、服务器部署、正式 AppID），而非业务功能缺失。按上述计划执行，可以将当前 demo 改进为可正式上线运营的小程序。
