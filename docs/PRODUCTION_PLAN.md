# 上线改进计划

## 业务场景（已更新）

- **单店、约 5 名员工**
- **客源混合**：线上小程序预约 + 线下上门 + 电话预约
- **核心痛点**：不知道某个时间段还能不能接客，目前全靠人工记忆和电话沟通
- **目标**：让小程序成为"门店容量中控台"——线上顾客自助查看和预约、店员实时管理所有渠道的占位

---

## 现状评估

### 当前代码假设 vs 实际需求

| 维度 | 当前代码 | 实际需求 |
|------|---------|---------|
| 员工数 | 1 人（每时段最多 1 单） | ~5 人（每时段可同时服务多人） |
| 客源 | 仅线上预约 | 线上 + 线下上门 + 电话 |
| 容量模型 | 有人预约就占满 | 按在岗人数动态计算剩余位置 |
| 店员操作 | 只能审核线上预约 | 还需要为线下/电话客户占位 |
| 容量调整 | 关闭整天 | 某天少人上班时调低容量 |
| AppID | `touristappid` | 需正式 AppID |
| 微信登录 | Mock OpenID | 需 `wx.login` |
| 部署 | `http://127.0.0.1:3000` | 需 HTTPS + 云服务器 |

## 改进计划

### 阶段一：容量模型改造（P0 - 业务核心）

**目标**：从"单员工、每时段 1 单"升级为"多员工、每时段 N 位容量"。

#### 1.1 预约规则数据模型升级

当前：
```json
{
  "advanceOpenDays": 7,
  "closedDates": ["2026-03-20"],
  "dailySlots": ["10:00-11:00", "14:00-15:00"]
}
```

升级为：
```json
{
  "advanceOpenDays": 7,
  "closedDates": ["2026-03-20"],
  "dailySlots": ["10:00-11:00", "14:00-15:00"],
  "defaultCapacity": 5,
  "capacityOverrides": {
    "2026-03-22": 3,
    "2026-03-25": 4
  }
}
```

- `defaultCapacity`：默认每时段可同时服务人数（≈ 在岗员工数）
- `capacityOverrides`：按天覆盖容量（某天有人请假就改小）
- 不配置 override 的日期自动使用 `defaultCapacity`

#### 1.2 Availability 计算逻辑改造

当前逻辑：有 1 个 `approved` 预约 → 时段不可约

新逻辑：
```
某日某时段剩余容量 = getCapacity(date) - approved预约数 - 店员手动占位数
剩余 > 0 → 可约（返回剩余数量）
剩余 = 0 → 已约满（不返回该时段，或标记为 full）
```

API 响应升级：
```json
{
  "items": [
    {
      "date": "2026-03-22",
      "timeSlot": "10:00-11:00",
      "status": "active",
      "capacity": 3,
      "booked": 1,
      "remaining": 2
    }
  ]
}
```

#### 1.3 数据库 `appointments` 表改造

新增 `source` 字段区分预约来源：
- `online` — 顾客通过小程序线上预约
- `walk_in` — 店员为线下上门客户占位
- `phone` — 店员为电话客户占位

新增 `created_by_staff` 字段，记录是哪个店员操作的占位。

#### 1.4 移除单时段唯一索引

当前有 `UNIQUE INDEX ON appointments(date, time_slot) WHERE status = 'approved'`，限制每时段只能 1 个 approved。需要移除，改为在代码中做容量校验。

#### 1.5 预约创建时的容量校验

- 线上顾客提交：检查剩余容量 > 0，否则返回 `SLOT_FULL`
- 店员审核通过：检查剩余容量 > 0，否则返回 `SLOT_FULL`
- 店员占位：检查剩余容量 > 0，否则提示已满

### 阶段二：店员快速占位功能（P0 - 解决线下客源痛点）

**目标**：店员可以 1 秒内为线下/电话客户占一个时段位置。

#### 2.1 新增后端接口

```
POST /api/v1/staff/reservations
Header: X-Staff-OpenId
Body: {
  "date": "2026-03-22",
  "timeSlot": "10:00-11:00",
  "source": "walk_in",       // walk_in | phone
  "customerName": "张小姐",   // 选填
  "phone": "138xxx",          // 选填
  "note": "做法式"            // 选填
}
```

逻辑：
- 校验店员身份
- 检查剩余容量
- 直接创建一条 `status=approved` 的预约记录（无需审核流程）
- 返回创建结果

```
DELETE /api/v1/staff/reservations/:id
Header: X-Staff-OpenId
```

逻辑：释放一个占位（客户取消了）

#### 2.2 新增前端页面：店员今日面板

新页面 `pages/staff/dashboard/index`，核心功能：

```
┌─────────────────────────────────┐
│  2026-03-22（今天）    [切换日期]  │
├─────────────────────────────────┤
│  10:00-11:00                    │
│  ██░░░  2/5                     │
│  • 张小姐(线上) 待审核           │
│  • 李小姐(上门) 已占位           │
│  [+ 占位]                       │
├─────────────────────────────────┤
│  11:30-12:30                    │
│  █░░░░  1/5                     │
│  • 王小姐(电话) 已占位           │
│  [+ 占位]                       │
├─────────────────────────────────┤
│  14:00-15:00                    │
│  ░░░░░  0/5                     │
│  暂无预约                       │
│  [+ 占位]                       │
└─────────────────────────────────┘
```

功能要点：
- 一眼看清每个时段的容量使用情况
- 一键占位（电话/上门客户来了直接点）
- 一键释放（客户取消了直接滑删）
- 切换日期查看和管理未来几天
- 每个预约条目显示来源（线上/上门/电话）和状态

#### 2.3 店员端页面整合

当前店员有 2 个页面：规则配置 + 预约审核。新增后调整为：

| 页面 | 路径 | 功能 |
|------|------|------|
| 今日面板 | `pages/staff/dashboard` | 查看容量、快速占位/释放、审核预约（**店员最常用**） |
| 预约规则 | `pages/staff/rules` | 配置时间段、容量、休息日 |
| 预约管理 | `pages/staff/appointments` | 按状态筛选、审核线上预约 |

将"今日面板"作为店员端首页，因为这是店员每天最高频使用的页面。

### 阶段三：微信登录与真实身份接入（P0 - 上线必须）

#### 3.1 后端：接入微信登录

- 新增 `POST /api/v1/login` 接口
  - 接收前端 `wx.login()` 的 `code`
  - 调用微信 `jscode2session` 换取 `openid` + `session_key`
  - 生成登录态 token
  - 返回 token 给前端
- 新增环境变量：`WECHAT_APP_ID`、`WECHAT_APP_SECRET`
- 后续所有鉴权接口从 token 解出 openId

#### 3.2 前端：替换 Mock 身份

- `app.js` 的 `onLaunch` 中调用 `wx.login()` → 后端换 token
- `utils/request.js` 统一注入 `Authorization: Bearer <token>`
- 移除开发环境的 mock OpenID 手动输入

#### 3.3 店员登录

- 店员同样走 `wx.login` 获取 openId
- 后端校验 openId 是否在白名单中
- 移除手动输入 OpenID 的交互

### 阶段四：服务端部署与域名配置（P0 - 上线必须）

#### 4.1 服务器部署

- **推荐方案：微信云托管**
  - 零运维，自动 HTTPS，免备案
  - Docker 容器部署
  - 适合当前单店场景
- **备选方案：自有服务器**
  - 腾讯云/阿里云轻量应用服务器
  - 域名备案 + SSL + Nginx + Docker

#### 4.2 Dockerfile

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY apps/server/ ./
RUN mkdir -p /app/data
EXPOSE 3000
CMD ["node", "src/server.mjs"]
```

#### 4.3 数据持久化

- 挂载数据卷，容器重启不丢数据
- 定时备份 SQLite 文件到对象存储

#### 4.4 小程序域名配置

- 微信公众平台配置 `request 合法域名`
- 前端 `apiBaseUrl` 按环境区分

## 结论

当前项目的代码骨架和 API 设计质量良好，但业务模型假设（单员工、仅线上）与实际场景（5 员工、线上+线下混合）存在根本差异。**最高优先级是改造容量模型和增加店员占位功能**，这两项改完后，小程序才能真正解决"不知道还能不能接客"的核心痛点。基础设施层面的改进（登录、部署、AppID）可以与业务改造并行推进。
